# CLAUDE.md

This file provides guidance to Claude Code (claude.ai/code) when working with code in this repository.

## Project overview

warawara is a browser-based avoidance game (ブラウザーで遊べるシンプルなゲーム). The player character follows the mouse cursor; after 30 seconds, virus-like enemies spawn from screen corners and are pulled toward the player by a gravity-like force. Touching an enemy ends the game; survival time is the score.

There is no build system, package manager, or bundler for the game itself — it's plain HTML5 Canvas + vanilla JS using native ES modules (`<script type="module">` in [web/index.html](web/index.html)). The game's web assets live under `web/` (rather than the project root) because that's what the Tauri desktop wrapper (see below) requires as its `frontendDist`.

## Running the game

### As a plain web page

Because `index.html` loads modules via `<script type="module">`, opening the file directly (`file://`) fails with a CORS error. Serve it over HTTP instead:

```bash
npx serve web
```

or

```bash
python3 -m http.server 8000 --directory web
```

Then open the printed localhost URL in a browser.

### As a desktop app (Tauri)

The project is also wrapped as a Tauri v2 desktop app (`src-tauri/`), pointing its `frontendDist` at `web/` unchanged — no game logic is duplicated or rebuilt for desktop.

```bash
cargo tauri dev    # run with a live window
cargo tauri build  # produce a standalone installer/bundle under src-tauri/target/release/bundle/
```

**Prerequisites (per OS this has been or will be built on):**

- **All platforms**: Rust via [rustup](https://rustup.rs) (stable), and the Tauri CLI: `cargo install tauri-cli --version "^2.0.0" --locked`.
- **macOS** (already set up, Phase 1 done here): full **Xcode** installed (not just the Command Line Tools — the CLT alone is insufficient for desktop builds).
- **Windows** (already set up, working end-to-end): Rust via rustup with the `stable-msvc` toolchain, **Microsoft C++ Build Tools** (installed with the "Desktop development with C++" workload), and **WebView2** (preinstalled on Windows 10 1803+/11; otherwise install the Evergreen Bootstrapper). Docs for older Tauri/WiX versions mention the **VBSCRIPT** optional Windows feature being required for MSI bundling — on the Windows 11 machine this was verified on, `cargo tauri build` produced both the MSI and NSIS bundles with no VBSCRIPT-related issue and no manual feature-enabling step, so treat that requirement as conditional/version-dependent rather than a hard prerequisite; only chase it if MSI bundling actually fails with a related error.
- **Linux** (not yet done): Rust via rustup, plus distro packages — e.g. on Debian/Ubuntu: `libwebkit2gtk-4.1-dev build-essential curl wget file libxdo-dev libssl-dev libayatana-appindicator3-dev librsvg2-dev` (package names differ on Fedora/Arch).

**Cross-platform builds do not cross-compile from one host.** `cargo tauri build` produces a bundle only for the OS it runs on (Windows bundles land in `src-tauri/target/release/bundle/msi/` and/or `nsis/`, Linux in `deb/`/`appimage`/`rpm/` depending on `bundle.targets` in `tauri.conf.json`, macOS in `macos/`+`dmg/`). Getting all three requires running the build on (or via CI for) each target OS — this repo currently has macOS and Windows builds done; Linux is future work.

**`src-tauri/target/` is a large (multi-GB), OS/arch-specific Rust build cache** — it regenerates from source and is useless on a different OS, so exclude it from any file sync (this repo currently syncs via Synology Drive rather than git, so there is no `.gitignore` enforcing this — `src-tauri/target/` should be added to Synology Drive's sync-exclude list, or the repo should be put under git with `src-tauri/.gitignore` — already generated by `cargo tauri init` — respected instead).

There is no test suite, linter, or build step configured for the game logic itself (`test/` is currently empty).

## Architecture

All game logic lives in `web/src/` as ES modules, wired together in [web/src/game.js](web/src/game.js):

- **`Game` class ([web/src/game.js](web/src/game.js))** — owns the canvas, the `requestAnimationFrame` loop, and all game state. Flow: **title** → click START runs a 3-second countdown (`beginCountdown()`) → `startGame()` sets `this.started = true`, records `startTime`/`lastScoreTick`, resets `score`, spawns the first enemy → **playing** → a player-enemy collision calls `triggerGameOver()`, which freezes the player (its `update()` is skipped from then on), records the run to the score history (`recordScore()`, see below), and sends every enemy into "converging" mode (see `Enemy` below) → **game over** — once every enemy has `arrived` at the frozen player position, the `#gameover-screen` overlay (yellow "Game Over", "Back to Title" button, then the score history table) is shown → clicking the button calls `resetToTitle()`, which clears `enemies`, resets all the flags/score, and shows the title screen again (no page reload — the score history table itself is left as-is, since it's meant to persist across runs). `loop()` always updates/draws the player and the 4 corner `Launcher`s regardless of state (so the player can move around them on the title screen too); enemy spawning, the timer/warawara-count/score updates, and collision checks only run once `started`, and are skipped once `gameOver` (except the enemies' own per-frame `update()`/`draw()`, which keeps running so the convergence animation plays out — everything else, including the score, is frozen at its value at the moment of collision). The on-screen stats (`#warawara-count`, `#time-count`, `#score-count`, stacked inside `#ui`) update together in that same guarded block: `score` accrues in fixed 100ms real-time ticks (a `while (now - lastScoreTick >= 100)` catch-up loop, not tied to frame rate) — each tick adds `1 + (n-1)*n*0.1` points where `n` is the *current* live enemy count, so more enemies on screen scores faster. The displayed score is floored with a `+1e-9` epsilon (`Math.floor(this.score + 1e-9)`) to avoid floating-point sums like `15.999999999998` from displaying one point low.
- **Score history / leaderboard** (`recordScore()`/`renderScoreHistory()` in [web/src/game.js](web/src/game.js)) — persisted in `localStorage` under the key `warawara-score-history` (module-level `loadScoreHistory()`/`saveScoreHistory()` helpers, both defensively wrapped in try/catch since storage can throw/be unavailable). On every game over, `recordScore()` snapshots `{date, mode, warawara, time, score, total}` (`mode` is `this.mode` at collision time; `warawara`/`time`/`score` are the frozen final values). `renderScoreHistory()` reads `entry.mode ?? '-'` so history entries saved before this field existed still render (as `-`) instead of showing `undefined`. `total` is `score` normalized by screen size: `Math.round(score * REFERENCE_SCREEN_SIZE / maxScreenSize)`, where `REFERENCE_SCREEN_SIZE` is a fixed constant (1000px) and `maxScreenSize` is the *largest* square canvas size seen during the run (tracked in `resize()`, not just the size at collision) — this normalizes for the fact that a bigger screen gives more room to dodge, and using the max-seen size (rather than the current size) specifically prevents shrinking the window right before a collision to cheat a better score. This has changed at least once already (an earlier version used a geometric-mean-of-three formula, `Math.round(Math.cbrt(warawara * time * score))`) — check the current `recordScore()` source before assuming either description is still accurate, since this project syncs across machines via Synology Drive rather than git and a formula change on one machine won't otherwise show up here. The list is sorted descending by `total` and truncated to the top 10 (`SCORE_HISTORY_LIMIT`) before saving, then re-rendered into `#score-history-body` as table rows via `document.createElement('td')` + `textContent` (deliberately *not* `innerHTML`/template-literal-built markup — `localStorage` is writable by anything same-origin, including the user via devtools, so treat its contents as untrusted; see the security note below). Since this uses plain `localStorage`, it works identically in the browser build and inside the Tauri WebView with no platform-specific code, but is scoped per-origin — the Tauri app's history and a browser-tab's history (e.g. via `python3 -m http.server`) are separate and don't share data.
- **Mode selection** (title screen) — `#mode-select` in [web/index.html](web/index.html) lists 4 `.mode-option` elements (`data-mode="free"|"normal"|"dazzle"|"expert"`, labeled "Free/Normal/Dazzle/Expert mode"). `Game` reads them into `this.modes` (constructor), defaults `selectedModeIndex` to `"normal"`, and lets the player change it by clicking an option or with Up/Down arrow keys (`handleModeKey()`, only active while the title screen is visible — gated on `!titleScreen.classList.contains('hidden')`, with wraparound at both ends). `selectMode(index)` updates the `.selected` CSS class (the highlighted pill) and the index; `startGame()` captures the choice into `this.mode`. **Three modes have real behavior so far**: `"normal"` is today's game as described elsewhere in this file; `"free"` is identical except the player-enemy collision check in `Game.loop()` is skipped (`if (this.mode !== 'free' && checkCollision(...))`), so there's no game over — warawara just keep accumulating forever. Because Free mode never reaches the game-over screen (its only other exit), it needs its own way back to the title: an always-on-top `#free-mode-exit-button` ("Back to Title", shown/hidden by `startGame()`/`resetToTitle()` toggling its `.visible` class, wired to `resetToTitle()`) plus an Escape-key shortcut (`handleFreeModeExitKey()`, desktop-only convenience — the button is what makes this work on touch/mobile too). `"dazzle"` is `"normal"` plus two changes: (1) `Game.loop()` draws `DazzleBackground` (see below) instead of a plain `clearRect` each frame, and (2) every 100ms score tick is multiplied by `DAZZLE_SCORE_MULTIPLIER` (1.3). `"expert"` is `"normal"` plus the `DazzleBackground` (same as Dazzle mode, drawn whenever `mode === 'dazzle' || mode === 'expert'`), a set of spinning `Wall`s (see below) created in `startGame()` via `spawnWalls()` and cleared in `resetToTitle()`, and an `EXPERT_SCORE_MULTIPLIER` of 1.7 on every score tick.
- **`DazzleBackground`** ([web/src/dazzleBackground.js](web/src/dazzleBackground.js)) — the animated background shared by Dazzle *and* Expert mode: 4 large, soft, semi-transparent "blobs" that continuously drift along independent sinusoidal (Lissajous-style) paths, slowly pulse in radius, slowly rotate through hue, and periodically crossfade between shapes (`SHAPES = ['circle','square','triangle','pentagon','hexagon','star']`, via `drawShape()` clipping a radial gradient to the target polygon/star path — see `addPolygonPath()`/`addStarPath()`), all layered on a fixed dark base fill. On top of that, `drawStripes()` sweeps a handful of wide diagonal bands whose angle (`stripeAngle`) drifts continuously and whose sweep direction/speed wanders and can reverse (driven by a slow `Math.sin` oscillator), fading in/out via a slow intensity oscillator rather than popping on/off. The whole thing runs at a variable tempo: `updateTempo()` eases `speedMultiplier` toward a new random target every ~1.5–4s, so motion visibly surges and eases back down — "sudden" in feel, but continuous in value (nothing's position ever teleports; only its rate of change does), and every animated quantity (drift, pulse, hue, shape rotation, stripe angle/sweep) is scaled by this same multiplier for a cohesive tempo. `draw(ctx, width, height)` is called once per frame from `Game.loop()`; it holds all its own state (blob configs, tempo, stripe phase/angle) and has no per-run reset logic, so it doesn't need to be recreated between games. **Deliberately designed to be disorienting without being unsafe**: no discrete flashing or hard on/off contrast changes anywhere (only continuous, gradual change — nothing near the ~3Hz+ range that triggers photosensitive seizures, and tempo/shape/stripe transitions are all eased, not instant), no screen-shake/camera movement (avoids vestibular/motion-sickness triggers), stripes are few and wide rather than a fine repeating pattern (avoids pattern-sensitive-epilepsy risk), and alpha/luminance are kept moderate throughout (`BLOB_ALPHA = 0.3`, stripe intensity capped ~0.28, on a dark, never-pure-black-or-white base) so the scene never gets close to a bright flash. If you tune this further (this has already been made more intense once, at the user's request, after the initial version was judged too tame), preserve those constraints — the goal is "harder to visually track," not literally strobing.
- **`Wall`** ([web/src/wall.js](web/src/wall.js)) — Expert-mode obstacle: a medium-thick (`thickness = 8`) white line segment of fixed `length` that spins in place around its own `centerX`/`centerY` at a constant `angularVelocity` (radians/frame, sign = spin direction). `closestPoint(px, py)` returns the closest point on the segment to `(px, py)` plus `t`, the signed distance of that point from the center along the wall's own axis — this `t` is what lets `flingOffWall` (physics.js) compute the wall surface's rigid-body tangential velocity at the contact point (`angularVelocity * t`, direction `(-sin(angle), cos(angle))`), scaled up by `FLING_BOOST` for a dramatic launch rather than a physically-accurate nudge, and (for enemies only, via `entity.vx !== undefined`) also sets `entity.speedMultiplier = ENEMY_WALL_SPEED_BOOST` — see the `Enemy` entry below for why that's needed on top of the velocity boost. `flingOffWall` is called for both the player and every enemy each frame in `Game.loop()`, guarded by `mode === 'expert'` and (for the player) `!gameOver`. **Tunneling fix**: the player jumps straight to the mouse position every frame (unlike enemies, which move in small capped steps), so a single point-in-time collision check can skip clean over the wall's thin hit-band without ever registering — call site passes the player's pre-move position (`prevPlayerX`/`prevPlayerY`, captured in `Game.loop()` before `player.update()`) as `flingOffWall`'s optional `fromX`/`fromY`, which makes it sample `WALL_SWEEP_SAMPLES` (16) points along this frame's movement path and resolve at the first one that overlaps the wall — this is what actually prevents "passing through". Enemies don't pass `fromX`/`fromY`, so they get the cheaper single-point check. `spawnWalls()` (in `Game`) picks a wall count from screen size (`EXPERT_WALL_BASE_COUNT` (2) plus one more per `EXPERT_WALL_COUNT_STEP_SIZE` px of canvas size beyond `EXPERT_WALL_COUNT_BASE_SIZE`) and places them by splitting the full circle around the canvas center into that many even angular slices (each with a little random jitter, so it doesn't look mechanically rigid) — radiating outward rather than being purely randomly scattered, which was the previous approach and tended to cluster/overlap walls — with each wall's *distance* from center still randomized within a min/max band that keeps it away from both the exact center and the edges/launchers. Angular speed is randomized per wall between `EXPERT_WALL_MIN_ANGULAR_SPEED`/`EXPERT_WALL_MAX_ANGULAR_SPEED` (0.29–0.43 rad/frame, sign randomized separately for spin direction) — these have been tuned by feel multiple times (twice faster, most recently a slight slowdown from 0.32–0.48), so don't assume the current numbers are final without checking the source.
- **`Player` ([web/src/player.js](web/src/player.js))** — position is set directly from `Input.mouseX/mouseY` each frame, then clamped into `[radius, canvasWidth/Height - radius]` so the player can't be dragged off-screen (`input.js` itself doesn't clamp, e.g. if the mouse leaves the canvas). No other independent physics. `Game.loop()` also pushes it back out of any `Launcher` it overlaps (`pushOutOfCircle`) — the launchers are solid to the player but never end the game.
- **`Enemy` ([web/src/enemy.js](web/src/enemy.js))** — spawns at a random corner with an initial velocity aimed at the player (random speed 2.0–5.0). Normally, each frame it accelerates toward the player's *current* position using an inverse-square "gravity" pull (tunable via the `G` constant and the distance floor in `update()`), capped at a max speed of `5.0 * this.speedMultiplier`, bounces off canvas edges by inverting velocity, and bounces off `Launcher`s via `reflectOffCircle` (mirrors velocity across the contact normal). `speedMultiplier` defaults to 1 and eases back toward 1 every frame (`SPEED_BOOST_DECAY = 0.9823`, ~3–6s to mostly settle — deliberately twice as slow as an earlier 0.965/~1.5–3s version, per user feedback) — it only goes above 1 when `flingOffWall` (physics.js) knocks the enemy off an Expert-mode `Wall`, which sets it to `ENEMY_WALL_SPEED_BOOST` (2, also raised from an earlier 1.5), i.e. a wall hit temporarily raises the enemy's normal top speed to 10.0 rather than just redirecting it. This exists because the speed cap runs every frame *before* movement, so without a temporarily-raised ceiling, the large one-off tangential velocity `flingOffWall` adds (see `FLING_BOOST` below) would just get clamped straight back down to 5.0 on the very next frame — flinging would only ever change an enemy's *direction*, never let it actually move faster than normal, however hard it was hit. Calling `startConverging(targetX, targetY)` (done once, from `Game.triggerGameOver()`) switches it into a one-way mode: it ignores gravity/walls/launchers and rushes in a straight line at a fixed high speed toward that point, setting `this.arrived = true` and stopping once it gets there — this is what makes the enemies swarm and pile up on the frozen player at game over.
- **`Launcher` ([web/src/launcher.js](web/src/launcher.js))** — one per corner (`top-left`/`top-right`/`bottom-left`/`bottom-right`), purely a static obstacle with no behavior of its own. `update(canvasWidth, canvasHeight)` recomputes its `x`/`y`/`radius` from the *current* canvas size every frame (so it tracks its corner correctly even if the window is resized), then `draw()` renders a quarter-circle sector with a small rounded bulge on the diagonal toward screen center. Collision against it is a plain circle test (`entity.radius + launcher.radius`) even though the drawn shape is a quarter-circle — that's intentional and safe *only* because each launcher sits exactly on a canvas corner, so the other 3 quadrants of its collision circle are never reachable by anything on-canvas.
- **`physics.js`** — free functions operating on generic `{x, y, radius}` (and `{vx, vy}` where noted) objects, not tied to any class: `checkCollision(a, b)` (circle-circle distance test, used for player-vs-enemy game-over detection), `resolveCollision(e1, e2)` (elastic collision + overlap separation between two *movable* circles, used for enemy-vs-enemy bounces), `pushOutOfCircle(entity, obstacle)` (positional-only correction against an *immovable* circle, used for player-vs-launcher), and `reflectOffCircle(entity, obstacle)` (like `pushOutOfCircle` but also mirrors `entity.vx/vy` across the contact normal, used for enemy-vs-launcher).
- **`Input` ([web/src/input.js](web/src/input.js))** — tracks raw mouse coordinates relative to the canvas via a `mousemove` listener; this is the only input source (no keyboard/touch handling — relevant if a future mobile/Tauri-mobile build is added).
- **`Music`** ([web/src/music.js](web/src/music.js)) — the in-game background track: a four-on-the-floor loop synthesized live with the Web Audio API (kick, hi-hat, off-beat bass stab, no audio file assets), using the standard "lookahead scheduler" pattern (schedule ~100ms ahead of `AudioContext.currentTime`, re-check every `LOOKAHEAD_MS` via `setTimeout`) for sample-accurate timing. `scheduleStep(step, time, tier)` works on a 16-step (sixteenth-note) grid per bar: kick on steps 0/4/8/12 (the four quarter-note beats), bass on the off-beat steps 2/6/10/14. **Intensity scales in tiers with the live warawara count** (`setEnemyCount()`, called every frame from `Game.loop()`, sets `tier = min(MAX_TIER, floor(enemyCount / ENEMIES_PER_TIER))` — currently one tier per 10 enemies): each tier adds `BPM_STEP_PER_TIER` to the tempo and opens up the bass's lowpass filter (brighter/more present); from tier 1 the hi-hat switches from the sparse off-beat pattern to playing on every step; from tier 2 a clap layers onto beats 2 & 4 (steps 4/12). Because the scheduler only looks ~100ms ahead, a tier change (read fresh at each `scheduleStep` call) audibly takes effect within roughly one beat, not instantly or with a jarring jump. **Two-phase startup, because of browser autoplay policy**: `ensureContext()` (create/resume the `AudioContext`) must run synchronously inside a user-gesture handler, so `Game` calls it directly in the START button's click listener; actual note scheduling only begins later when `start()` runs from `startGame()` (after the countdown) — `start()` calls `ensureContext()` too, so it's safe to call on its own if some future caller doesn't have a click handler to hook. `stop()` is called from both `triggerGameOver()` (so the beat cuts immediately on collision rather than continuing through the convergence animation) and `resetToTitle()` (covering Free mode's non-collision exits). `toggleMute()`, wired to `#mute-button` (shown/hidden alongside `#ui`), only touches `masterGain.gain` — it doesn't stop the scheduler, so unmuting resumes in the middle of the beat rather than restarting the loop.

Key coupling to keep in mind when changing behavior:
- Enemy movement depends on the *live* `Player` object reference (passed into `Enemy.update`), not a snapshot — gravity always pulls toward the player's current position (except while `converging`, which targets a fixed point captured at collision time, not the live player).
- The canvas is always kept square (`min(innerWidth, innerHeight)`) per the game's stated requirement; `resize()` is called on load and on window `resize` events, but entity positions (other than `Launcher`, which recomputes from scratch every frame) are not rescaled when the canvas resizes mid-game.
- Enemy spawn cadence past the 30s mark is probabilistic (`Math.random() < 0.02` per eligible frame) rather than a fixed timer — see `Game.loop()` in [web/src/game.js](web/src/game.js).
- The gravity constant `G` in `web/src/enemy.js` has been tuned empirically (not derived from the original spec) — changing canvas size or speed caps will change how strong the pull feels, since the force falls off with the square of pixel distance.
- The canvas has `cursor: none` (the player circle acts as the visible cursor) — `Game` explicitly flips it back to `'default'` in `triggerGameOver()` and to `'none'` again in `resetToTitle()`; don't remove those without re-checking cursor visibility during game over.
- `src-tauri/tauri.conf.json`'s window config has `"maximized": true`, so the desktop build opens maximized by default; the browser build is naturally always "maximized" (fills the tab).

## Security notes

A manual audit (no server/network/accounts here, so most of the OWASP Top 10 doesn't apply) found two things worth knowing when touching related code, both since fixed:

- **`src-tauri/tauri.conf.json`'s `app.security.csp`** is now a real policy (`default-src 'self'; script-src 'self'; style-src 'self' 'unsafe-inline'; object-src 'none'; base-uri 'self'; form-action 'self'`) rather than `null`. `style-src` needs `'unsafe-inline'` because [web/index.html](web/index.html)'s CSS lives in an inline `<style>` block; if that ever moves to an external stylesheet, `'unsafe-inline'` could be dropped from `style-src` too. There's no equivalent hole in `script-src` — everything loads as an ES module file, never inline/`eval`.
- **`renderScoreHistory()` builds table rows with `document.createElement('td')` + `textContent`, not `innerHTML`/template literals** — score history round-trips through `localStorage`, which anything same-origin (including the user via devtools) can write to, so treat its contents as untrusted input. Keep new fields rendered the same way; reintroducing an `innerHTML`-with-interpolated-data pattern here (or for any other localStorage-sourced data) would reopen a stored-XSS path, low-impact today only because nothing else in the app currently trusts DOM content that a page script could plant.
- `cargo audit` (run manually — not wired into any script/CI here) found no exploitable-severity advisories against `src-tauri/Cargo.lock`, only a handful of "unmaintained"/"unsound" warnings in indirect dependencies pulled in by Tauri/wry itself; worth re-running after Tauri version bumps.

A later written report, [docs/security_report.md](docs/security_report.md), raised 9 further findings (SEC-001 through SEC-009); the ones acted on:
- **SEC-001** — `loadScoreHistory()` now runs every parsed entry through `isValidScoreEntry()` (checks `mode` is one of the 4 known modes, `warawara`/`time` are non-negative integers, `date`/`score`/`total` are finite non-negative numbers) and filters out anything that doesn't pass, rather than trusting `JSON.parse(localStorage...)`'s shape blindly.
- **SEC-002** — enemy spawning was previously capped only by `Math.floor(elapsed / 10)`, unbounded over a long session (a real concern given `Game.loop()`'s O(n²) pairwise `resolveCollision` check, and that Free mode is designed to never end). `computeMaxEnemies(canvasWidth, canvasHeight)` now also caps it — area-based (`MAX_ENEMIES_AREA_PER_ENEMY` px² per allowed enemy), floored at `MAX_ENEMIES_FLOOR` (20) so small windows aren't overly restricted. **Deliberately no upper hard cap** (an initial `MAX_ENEMIES_HARD_CAP` of 400 was added then removed at the user's request): the game's point is that avoiding warawara eventually becomes impossible, including on ultrawide/very large displays, so the screen should be able to fill up completely rather than plateau at a fixed count — on a 1440×1440 canvas this now allows 518 enemies where the old hard cap would have held it at 400. This is a static area-based heuristic, not a runtime frame-time measurement — if some real machine/resolution combination turns out to struggle, an adaptive (measure actual frame time, throttle spawning if it's climbing) approach would be the next step up in sophistication.
- **SEC-003** — every `Music` sound-generating method (`playKick`/`playHiHat`/`playClap`/`playBass`) now disconnects its nodes in an `onended` callback, instead of leaving that to the AudioContext graph + GC — relevant because at high tiers a new note fires close to every 16th-note step.
- **SEC-004** — `resolveCollision()` (physics.js) now guards `distance > 0` before dividing by it, matching the guard `pushOutOfCircle`/`reflectOffCircle` already had; two enemies spawned at the exact same corner in the same frame would otherwise divide by zero and propagate `NaN` into their velocities permanently.
- **SEC-009** — `Input`'s constructor now takes `canvas` as a parameter (`new Input(this.canvas)` in `Game`) instead of doing its own `document.getElementById('gameCanvas')` internally.

Deliberately **not** acted on (asked about, user declined): SEC-005 (externalizing the inline `<style>` block to drop `'unsafe-inline'` from the CSP — low real-world risk in a local-only app, and the report itself marked it optional), SEC-008 (a `Game.destroy()` lifecycle method for listener cleanup — `new Game()` is only ever called once, so there's nothing to clean up yet). SEC-007 (server-side score validation) is explicitly future-only — there's no server.

SEC-006 (`Cargo.toml`'s placeholder `authors`/`license`) was partially resolved later: the project settled on the **MIT License** (see [LICENSE](LICENSE) and the License section in [README.md](README.md)), so `license = "MIT"` now reflects that in `src-tauri/Cargo.toml`. `authors = ["you"]` is still a placeholder — that wasn't part of the licensing decision and hasn't been revisited.

## App icon

The desktop app's icon is a custom, hand-built SVG illustration (not a photo/AI-generated raster image) depicting the game's enemy character as a sculpted 3D spiky sphere, designed and iterated in-chat before being finalized:

- **Design**: a shaded sphere (radial gradient, light source upper-left) with triangular cone-shaped spikes fused seamlessly into its surface — each spike is two flat-shaded triangular facets (light-facing side lighter, shadow side darker) meeting at a thin ridge line, which is what reads as a 3D pyramid rather than a flat wedge. Spikes come in two rings at different lengths/angles (an outer ring of 8 long spikes at 45° spacing, an interstitial ring of 8 shorter spikes at the 22.5°-offset angles between them) plus 8 small two-tone "nub" bumps scattered across the front face of the sphere, so spikes appear to protrude in many directions rather than radiating from one flat plane. The spike bases sit at a smaller radius than the core circle, and the core is drawn on top, which is what makes the join seamless (a hard circular edge, being smooth, reads as a natural equator rather than a seam). Background is the same dark navy-to-near-black radial gradient (`#2a2a4a` → `#101018`) as the in-game title screen, for visual consistency with the rest of the app.
- **Source**: the master artwork lives only as the SVG markup used to generate the raster assets below — it was authored directly (not stored as a checked-in `.svg` file in this repo) and rasterized once via a headless-browser canvas render at 1024×1024 (`<img>` of the SVG drawn into a `<canvas>`, then `canvas.toDataURL('image/png')`). If the icon needs to change again, the SVG will need to be recreated or the design re-derived from `src-tauri/icons/icon.png` (the largest flat PNG Tauri generates, closest to a "master" reference going forward).
- **Generation**: `src-tauri/icons/*` (the files listed in `tauri.conf.json`'s `bundle.icon` — `32x32.png`, `128x128.png`, `128x128@2x.png`, `icon.icns`, `icon.ico` — plus Android/iOS/Windows-Store variants not currently referenced by any config but generated as a free side effect) were produced from that single 1024×1024 master PNG via `cargo tauri icon <path-to-master.png>`, which writes into `src-tauri/icons/` by default (matching where `tauri.conf.json` already points, so no config changes were needed). Re-run that command with a new master PNG if the icon changes; don't hand-edit files under `src-tauri/icons/` individually since they're generated output, not source.
- **Iteration notes** (in case the design is revisited): three rounds of feedback shaped the final version — (1) initial flat-triangle spikes with a single shared gradient across the whole cluster read as flat/2D, fixed by splitting each spike into two flat-shaded facets; (2) all spikes sharing one radius/one ring read as a flat 8-point star rather than a sphere covered in spikes, fixed by adding the second interstitial ring plus front-face nubs; (3) at full 1024px resolution (as opposed to the small chat-preview render), the front-face nubs read as flat pasted-on decals and small white specular dots at spike tips combined with the main highlight to look unintentionally eye-like/face-like — fixed by giving nubs the same two-facet shading as the big spikes and removing the per-tip highlight dots, keeping only the single specular highlight on the core. **Takeaway if tuning further**: always check a render at the actual target resolution (not just a small chat-embedded preview) before finalizing, since faceting/highlight issues that are invisible at ~300px can look wrong at 1024px.
- **Build quirk hit while generating this**: `cargo tauri build`'s DMG-bundling step (`bundle_dmg.sh`, which drives Finder/`hdiutil` via AppleScript to set icon layout) failed once under this session's default command sandbox with a generic "failed to run bundle_dmg.sh" error and no further detail — the `.app` bundle itself built fine, only DMG packaging failed. Re-running the build without that sandbox restriction succeeded on the first try, so if this recurs, suspect sandboxing/automation-permission restrictions on Finder/`hdiutil` rather than a real bug in the icon files or `tauri.conf.json`.

## SBOM

`src-tauri/warawara.cdx.json` is a CycloneDX 1.5 JSON Software Bill of Materials, generated (not hand-written) via the official [`cargo-cyclonedx`](https://github.com/CycloneDX/cyclonedx-rust-cargo) subcommand:

```bash
cargo install cargo-cyclonedx --locked   # one-time
cd src-tauri
cargo cyclonedx --format json --spec-version 1.5
```

Re-run whenever `Cargo.lock` changes (dependency bump, etc.) to keep it current — there's no CI wired up to regenerate it automatically yet. Only `src-tauri/` (the Rust/Cargo side) has a dependency graph worth SBOM-ing; `web/` is plain vanilla JS with no `package.json` and zero third-party dependencies, so it contributes nothing to the SBOM. The generated file was validated against the official CycloneDX 1.5 JSON Schema (`bom-1.5.schema.json` plus the `spdx`/`jsf-0.82` sub-schemas it references) with Python's `jsonschema` library — 0 errors. If `--spec-version` is bumped later, re-validate against the matching schema version rather than assuming it still passes.
